## Branches
- `front`: mirror of upstream `github.com/9front/9front`, branch `front`. Treat as pristine 9front source; update it by fast-forward to `origin/front`, then merge it into `gcc` (and `gcc` into `main`, `nix`, `riscv`): merges since 2026-11-13, no rebase or force push of these public branches (`dist/docs/upstream.md`).
- `upstream`: fixes for 9front itself found on `gcc` (not about gcc), one commit each on `origin/front`, exported to `patch-upstream/` (README.md there). A new one goes on `gcc` and on `upstream`. The only branch that is rebased (onto the new `front`).
- `gcc` (work branch): the gcc port. Keep diffs against `front` minimal and reviewable. After merging `front`, regenerate the manifests (upstream mkfile changes add sources) and run `tests/static`.
- `main` (this worktree, `~/Devel/nfront/tree`; was `ui`): nfront, the distribution: `gcc` plus the GPU stack (gpu(4), the LinuxKPI with Linux's DRM drivers, Mesa), wsys and the ui framework. 9front code may change here where the distribution needs it. `nix`, `riscv`: ports on `gcc`. Work happens on `main`; the other branches are refs in this repository, with a worktree beside this one (`tree-gcc`, `tree-nix`, `tree-riscv`, `tree-upstream`) only when needed (`dist/bin/repos --worktrees=gcc,...`; a rebase in a worktree made for the while, `dist/docs/upstream.md`). Never switch this worktree to another branch: its working tree holds main's build.

## nfront: where the other parts are
Everything lives in `~/Devel/nfront` (`dist/` the distribution's repository, `toolchain/{gcc,rust,go}`, `tools/mcp`, `distfiles/`). Paths come only from `dist/paths.env`: scripts read them with `scripts/lib/paths.sh` (shell, after `ROOT=`) or `scripts/lib/paths.py` (`paths.get('GCC_DIR')`); never write a sibling path into a script. `dist/bin/status` shows each part against `dist/manifest.json`, `dist/bin/pin` pins them. Below, "9front-gcc", "9front-rust", "9front-go" mean those toolchains (GCC_DIR, RUST_DIR, GO_DIR).

## Build tool and manifests
- Go sources in `sys/src/cmd/build/` (`build.go`, `codegen.go`, `genheaders.go`, `paths.go`, `doc.go`); `build.exe` is built there and not checked in. Format of the manifests: `doc.go`.
- From `ARCH` the tool sets, unless already in the environment: `objtype`, `O` (8/6/7), `SUFFIX` (none for amd64, `.386`, `.arm64`: names of the per-arch manifests), `CONF` (pc, pc64, qemu), `TOOLPREFIX` (arm64: `aarch64-linux-musl-`), `CPUS`. `PLAN9` defaults to the git checkout. Without an argument it builds `build.json` of the current directory, else the tree's.
- `build.json` → `build.$ARCH.json` (from `scripts/gen/genbuild.py`), in order: `prep` (`scripts/build/prep-objtype.sh`: install dirs, `libgcc.a`; 386: 9front-gcc's i686-pc-plan9 libgcc, else the host's -m32 one with SSE2/cmov and a warning), libc, the libraries (`genlibs.py --list`), every `sys/src/lib*/klib.json` (kernel archives `klib*.a`), the programs (`gencmds.py --list`), on amd64 the Linux drivers (`linux`), APE's parts made with 9front-gcc's cross compiler (`ape`: `scripts/build/ape.sh` runs build.exe -D on sys/src/mesa (libvulkan.a), libffi, wayland, sdl3, glfw and installs wlsys; `scripts/gen/apeprogs.py`; skipped without the compiler, `check-install.py` then says `nocross`) and the Rust crates (`rust`, after `ape`: wsys links libvulkan.a; each `sys/src/cmd/*/rust.json` via `scripts/gen/rustcrates.py`, built by `scripts/build/cargo.sh` with 9front-rust's stage-1 rustc, for amd64, 386 (`i686-unknown-plan9`) and arm64 (`aarch64-unknown-plan9`); where `ape` makes no Mesa (386, arm64) with `-n`, without the default feature `gpu` (wsys composes on the processor, ui draws with vello_cpu); skipped without it, `check-install.py` then says `norust`), `kernelgen` (`scripts/build/gen-*.sh`: rebootcode.i, apbootstrap.i, etherm10g/sd53c8xx .i, initcode, `/boot/boot` + `$CONF.bootfs.paq`), the kernel, `install` (`elf2aout.py`: the a.out where 9boot loads it; `check-install.py -r`). `Pre`/`Post` steps run without a shell (split on spaces), hence `bash scripts/...`. Do not build a kernel manifest alone after building another arch: `kernelgen` writes arch-specific files into shared places (`sys/src/9/port/initcode.i`); an amd64 kernel with 386's initcode panics at boot ("boot process died: ... pc=0x200028"). `-clean` runs only the `Projects` (`scripts/build/clean.sh`). `-D` builds only what is out of date, like mk: per object gcc's `x.d` (`-MMD`, headers) plus a signature of the compile command; kernel libraries name their objects `x.k.o` (`Objtag`, klib.json), as they compile the userspace libraries' sources in the same directories; generated files that come out the same keep their time (`Clean` lists, `writefile`; the generator scripts replace their output only when it changes). A no-op `-D` run takes seconds and ends with the same files as a full build. Each manifest's source files compile in parallel, `CPUS` at a time (one gcc run per file); manifests run one after another.
- Kernel manifests: `sys/src/9/pc64/build.json` (hand-made), `pc/build.json` and `arm64/build.json` (`scripts/gen/genkernel.py`). `Config` holds the CONF sections, each element one CONF line; the tool generates `<conf>.c` (mkdevc + mkrootc), `errstr.h`, `../port/systab.h`. The `link` section calls only the first name's link function (as mkdevc).
- Library manifests: `sys/src/lib<x>/lib<x>[.arch].json` (userspace) and `klib.json` + `<arch>.json` (kernel); 9front's `reduce` (port file dropped when the machine dir has one) is replicated.
- Generators read the mkfiles: `genlibc.py`, `genlibs.py`, `gencmds.py` (`--probe` rebuilds `scripts/gen/cmds-broken*.txt`), `genkernel.py`, `genbuild.py`; per arch with `objtype=386|arm64`. `tests/static` fails if a checked-in manifest differs from its generator.
- 9front's boot loaders are not built by gcc: `scripts/guest/build-boot.sh` boots the built system and runs 9front's own mkfiles with 8c/6c/7c there.

## Guest, CD, tests
- `scripts/guest/boot-cli.sh` boots the built kernel in QEMU (serial console, Harvey's ufs as root); `scripts/guest/mkiso.sh` / `scripts/guest/mkdisk.sh` make the install CD / disk image in the guest, as 9front's `sys/lib/dist/mkfile` does. Installation profiles (`scripts/guest/profiles`: minimal, gpu, ui, full; all from main's build, a profile only leaves groups' files off the CD) with `PROFILE=`/`DEV=` of `stage-dist.sh`, or `dist/bin/mkcd PROFILE [-dev gcc,rust,go]`. Work dir `$CLI_DIR` (`nfront/cache/cli`, from `dist/paths.env`; `~/.cache/9front-cli` links there for the branches without `scripts/lib/paths.sh`). The ports' work dirs and the provenance cache are in `$CACHE` (`nfront/cache`).
- Self-hosting: `scripts/guest/build-self.sh` builds the whole tree in the guest with `build.exe` (GOOS=plan9) and the native gcc of 9front-gcc (`$GCC_DIR`), on an ext4 disk made from a copy (`$CLI_DIR/self.$objtype`, `ext4srv`; `objtype=386`: a 9pc guest with `/386/gnu`); the steps run as `scripts/build/rc/*.rc` (`build.go`: `plan9step`). It compares every object with the Linux build; `KEEP=1` reuses the copy. On 9front, `gccmk` (from `9front-gcc/plan9`, in `/$objtype/gnu/bin`) runs 9front's own mkfiles with gcc (userland only).
- Go: 9front-go (`$GO_DIR`, go1.27.3, plan9/arm64 ported there; `scripts/install.sh` makes `/$objtype/go`); `GO_OUT=$GO_DIR/out/$objtype` puts it on the CD (`stage-dist.sh`, `scripts/guest/boot/goproto`), as `RUST_OUT` does for `9front-rust`.
- `tests/run.sh` categories: static, asm, syscall, build, guest, boot, gui, disk, iso, rio, usb (`tests/README.md`). `tests/iso/drive.py` boots the CD to rio and types into it; `tests/vm.py` is the module for guest tests on the CD (rio, usb): boot to rio, QMP keys/mouse, an rc on the serial line.

## Debugging a hung guest
- `scripts/debug/qemu-ctl.py DIR type|ser|shot|hmp`: keys via QMP, screendumps, monitor commands, and a second rc on the serial line (QEMU needs `-qmp unix:DIR/qmp.sock,...` and the serial line as `DIR/serial.sock`; socket paths < 108 bytes).
- `scripts/debug/thread-dump.py DIR PID BINARY`: libthread procs and threads of a guest process with stacks (needs the unstripped binary from `/$objtype/bin`).
- Kernel: `qemu-ctl.py DIR hmp 'gdbserver tcp::1234'`, then `gdb amd64/bin/9pc64` and `target remote :1234`.

## Checks for gcc-vs-kencc differences (scripts/check, scripts/fix)
`cmp-struct-layout.sh` (struct sizes against a kencc reference: long 32 bit, pack honoured), `find-long-io.py` (long data in raw I/O), `find-spinloops.sh` (endless busy-waits in a kernel binary), `find-shortened-members.py` (member paths shorter than in 9front), `cmp-lp64.sh` (6c/6a/6l output under -m32 vs -m64), `fixulongmax.py`.

`.opencode/` at the repo root is unrelated tooling (opencode CLI agent), not part of the build.
